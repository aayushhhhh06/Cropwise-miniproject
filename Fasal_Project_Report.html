ABSTRACT

Farm planning relies on observations about crop choice, field size, weather, soil moisture, pH, organic matter, and nutrients. These observations are often kept informally, making it difficult to compare field conditions or maintain a simple record of estimates. Fasal is a responsive crop-yield management dashboard that brings these inputs and a lightweight crop-specific estimation model into one interface.

The public application is delivered as a static website through GitHub Pages. A user selects one of five supported crops—rice, wheat, maize, cotton, or sugarcane—and enters field measurements. Browser JavaScript validates the inputs, calculates a weighted soil-health score and estimated yield, displays a general recommendation, and saves submitted reports in the browser’s local storage. Reports can be reviewed, deleted, cleared, or exported as CSV. The layout adapts to desktop, tablet, and smartphone screens.

The repository also retains an optional Flask development backend. That implementation uses SQLite for persistent records and NumPy for the same type of crop-profile yield calculation, with HTML templates and JSON endpoints. It is distinct from the Pages deployment: GitHub Pages does not execute Flask or provide a shared database. As a result, reports entered on the public static site remain on that device and browser and do not synchronise across users or devices.

The application demonstrates a complete, accessible workflow for educational field reporting, while making the limits of its simplified model and storage explicit. Estimates should not replace laboratory soil testing or advice from a qualified agronomist.

Keywords: crop yield estimation, farm dashboard, soil health, JavaScript, browser storage, GitHub Pages, Flask, SQLite, NumPy.

Chapter 1

INTRODUCTION

1.1 Project Background

Digital tools can help farmers organise field observations and compare crop scenarios. However, a practical field log does not need to begin with a complex farm-management platform. A focused interface that records a small set of conditions, explains its estimate, and keeps a usable history can support learning and basic planning. Fasal was developed as a mini project to demonstrate that workflow in a responsive web application.

Fasal accepts crop type, farm area, temperature, soil moisture, soil pH, organic matter, nitrogen, and phosphorus. It calculates an indicative health score and yield from crop-specific reference profiles. The public version is a static website accessible through the repository’s GitHub Pages URL on modern phones and computers.

1.2 Problem Statement

Field measurements and yield expectations may be noted in separate places or estimated informally. Without a simple record interface, users may find it difficult to validate readings, compare reports over time, and keep estimates associated with a crop and field area. A solution must also be accessible on common screen sizes without requiring visitors to install an application.

1.3 Proposed Solution

Fasal provides a browser-based dashboard with a structured field form, input-range validation, crop-specific estimate, recommendation text, and a recent-report history. Users can export report history in CSV format. GitHub Pages hosts the static web interface; an optional Flask/SQLite version is retained in the repository for local backend development and demonstrations.

1.4 Objectives

  1. Provide a simple, responsive interface for entering field and crop observations.
  2. Validate numeric inputs against defined ranges before calculating an estimate.
  3. Calculate a weighted field-health score and crop-specific yield estimate.
  4. Keep a reviewable report history and provide CSV export.
  5. Publish the static website through GitHub Pages for access by URL.
  6. Document storage, model, and deployment limitations accurately.

1.5 Scope and Limitations

The static website supports five crops and seven numeric field measurements. It provides an educational score, per-acre estimate, total estimate, and rule-based recommendation. Reports are kept in browser local storage, which is scoped to the browser profile and device. There is no user account, shared cloud database, weather service, sensor integration, or synchronisation.

The reference values and weighted formula are illustrative rather than calibrated against local yield datasets. The tool does not account for cultivar, season, irrigation management, pests, disease, seed quality, or local agronomic conditions. Its estimates must not be used as a guarantee of production, financial return, or fertiliser prescription.

1.6 Methodology

  1. Requirement identification: define the crop inputs, estimate outputs, browser history, and mobile-friendly page structure.
  2. Interface design: adapt the existing green dashboard design and organise the workflow into form, estimate, recommendations, and history.
  3. Model implementation: encode crop-specific target profiles and a weighted score, with input ranges enforced at the form.
  4. Persistence and export: save reports to local storage and generate a CSV download in the browser.
  5. Publishing: serve the standalone HTML, CSS, and JavaScript from the repository root on GitHub Pages.
  6. Validation: check document/assets, form-to-script element references, browser storage workflow, and the deployed Pages response.

1.7 Expected Outcomes

The expected outcome is a publicly accessible, responsive application that calculates illustrative crop estimates, retains a local history, and clearly explains that data is not shared between devices. The repository’s optional Flask implementation demonstrates how a server-backed version could be built and tested locally.

Chapter 2

BACKGROUND AND RELATED WORK

2.1 Introduction

This chapter frames the project in relation to common approaches to farm record keeping and lightweight web delivery. It is a design-oriented review, not a systematic survey or a claim that Fasal has been validated in field trials.

2.2 Farm Records and Yield Estimates

Field logs can preserve measurements that help users compare conditions across observations. A digital form improves consistency by naming each input, showing units, and applying permitted ranges. Crop models can range from simple rule-based calculations to calibrated statistical and process-based models. Fasal intentionally uses a transparent, weighted heuristic suitable for demonstrating application flow; it is not trained on a yield dataset and should not be interpreted as a production-grade agronomic model.

2.3 Web Delivery Models

A static website consists of files that a web server can deliver without executing application code on the server. This makes it suitable for GitHub Pages and broadly accessible through a normal URL. Browser storage can preserve small amounts of user data locally, but it is not a substitute for authenticated, central persistence. A dynamic Flask application can accept requests and use a SQL database, but it requires a separate server host; GitHub Pages does not run Python processes.

2.5 Gaps and Design Considerations

For this project, the principal design challenge is to avoid implying capabilities that the deployment does not provide. The published website therefore identifies browser-local storage and describes calculations as estimates. A shared, multi-device history would require a hosted backend, database, authentication, data protection, and operational ownership; those components are outside the deployed Pages application.

2.6 Summary

Fasal combines a lightweight web interface with structured inputs and an explainable calculation. The choice of static deployment makes the website easy to publish, while local-only persistence and the non-calibrated model remain explicit limitations.

3.4 Estimation Workflow

  1. The form reads the selected crop and numeric inputs.
  2. Browser-native required/minimum/maximum checks and JavaScript guards validate the values.
  3. The crop profile supplies ideal temperature, moisture, nitrogen, phosphorus, and base yield.
  4. Component scores are clamped from 0 to 100 and combined using fixed weights.
  5. The interface displays a score, yield, fertility, nutrient statuses, and rule-based recommendation.
  6. On submission, the input and estimate are stored as a local browser report and added to history.

3.5 Security and Privacy

The Pages application does not require an account and sends report history to no application server; browser storage remains local to the browser origin. Users should avoid entering sensitive personal information and should export or back up data they need to keep. Clearing browser data or changing devices can remove access to the saved history. The separate Flask backend has no user authentication and is intended for local development unless security controls and a production database are added before deployment.

4.3 Crop Profiles and Health Score

Each supported crop profile contains target values and an illustrative yield baseline. The six score components represent temperature, moisture, pH, organic matter, nitrogen, and phosphorus. For a target value, closeness is mapped into a bounded component score. Organic matter is scaled to a three-percent reference and capped. The weighted total is rounded to an integer from 0 to 100.

S = round(0.18T + 0.17M + 0.18H + 0.14O + 0.18N + 0.15P)
T = clamp(100 - 7 × |temperature - ideal temperature|, 0, 100)
M = clamp(100 - 2.4 × |moisture - ideal moisture|, 0, 100)
H = clamp(100 - 30 × |pH - 6.7|, 0, 100)
O = clamp(organic matter / 3 × 100, 0, 100)
N, P = clamp(100 - 80 × |measured - ideal| / ideal, 0, 100)

The derived fertility indicator and yield use the following equations:

Fertility = round(clamp(0.98 × S + 2 × organic matter, 0, 100))
Yield per acre = round to 0.1 (base yield × (0.6 + S / 250))
Total yield = round to 0.1 (yield per acre × area in acres)

The app’s target profiles are configuration constants in the source; they are not verified recommendations. The reported total uses tonnes and the profile baseline is treated as tonnes per acre for display. Such simplified assumptions limit the scientific meaning of the output.

4.4 Recommendations and History

The recommendation logic checks moisture first, then nitrogen, phosphorus, and pH, and displays the first applicable general prompt. The history view presents the crop, local date, score, and yield. A report can be individually deleted; all history can be cleared after confirmation. The CSV export serialises saved reports for a spreadsheet tool. Storage exceptions are reported to the user rather than treated as successful saves.

4.5 Optional Flask and SQLite Backend

The repository retains app.py, schema.sql, and Jinja templates for local backend experimentation. Database initialization creates the SQLite report table and date index. The form route validates values and inserts them with parameterised SQL. /api/records returns saved records and estimates; /api/estimate validates and returns a non-persistent estimate. This backend is not invoked by the public GitHub Pages site.

4.6 GitHub Pages Deployment

The public website is hosted at https://aayushhhhh06.github.io/Cropwise-miniproject/. GitHub Pages is configured to deploy from the main branch at the repository root. It serves the root index.html together with static/app.js and static/styles.css. Changes merged to the publishing branch trigger a Pages build.

Chapter 6

RESULTS, CONCLUSION, AND FUTURE SCOPE

6.1 Results

The project delivers a public responsive dashboard with five crop profiles, a validated field-entry form, a crop-health estimate, yield and nutrient indicators, rule-based guidance, local report history, record deletion, clear-history control, and CSV export. The public static build is deployed at the GitHub Pages URL and verified to return the page and assets successfully.

A separate Flask/SQLite implementation is retained for local backend learning and provides persistent records and JSON estimate/history routes when run on a Python host. It is not the runtime behind the GitHub Pages URL. The browser and backend implementations have similar objectives but different storage locations and deployment requirements.

6.2 Conclusion

Fasal demonstrates an end-to-end crop reporting workflow using accessible web technologies. Hosting the front end on GitHub Pages provides a public URL without requiring users to install software. Browser-local storage keeps basic history without a server, while the report explains that this history is device-specific. The project fulfils its educational software objectives but does not establish the agronomic validity of its illustrative yield estimates.

6.3 Future Scope

  1. Evaluate the estimation model against trustworthy, local crop-yield datasets and seek review from qualified agronomists.
  2. Introduce a secured, hosted backend and managed SQL database for authenticated cross-device synchronisation.
  3. Add fields such as location, crop variety, season, sowing date, irrigation, and actual harvest to support meaningful comparisons.
  4. Support import, backup, and restore workflows in addition to CSV export.
  5. Improve language accessibility and conduct usability testing with intended users.
  6. Complete formal accessibility, browser compatibility, privacy, and security reviews before wider operational use.
  7. Integrate weather or sensor data only with reliable data sources, user consent, and clearly documented uncertainty.
